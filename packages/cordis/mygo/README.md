# @deepseek-ai/dsh-mygo

English | [中文](README.zh.md)

> **dsh-MYGO!!!!!** — Managed Yield Gen Orchestrator. Named after the band MyGO!!!!! (BanG Dream!). Every lost plugin finds its way home on boot.

The managed-plugin bridge between the Cordis-free upper contract (`@deepseek-ai/dsh-mygo-api`) and the harness runtime: the `ctx.pluginManager` service-key types, the manager deployment Config, and the §16 group-1/group-2 mount-time validation chain, the pure ordering/conflict/plan derivations, the containerized dispatch machine, the lifecycle engine, and the PluginEnv capability boundaries, and the sqlite persistence + boot-recovery layer. Stages #12–#20 are landed (factory integration details below); proposals A/B and the stage-one native-capability catalog extend the same error vocabulary.

First-time plugin authors start with the [plugin author guide](../../../docs/plugin-author-guide.md); the [ecosystem compatibility matrix](../../../docs/plugin-ecosystem-compat.md) records how existing dsh-external Cordis plugins migrate through `fromCordisPlugin`. Deployment-facing details (grants, quotas, the sqlite registry) live in this README.

## Public API

- `PluginManager` / `PluginOperation` / `PluginOperationPlan` The typed §15.3 service surface, also declared as the `ctx.pluginManager` key on the Cordis `Context`. The #12 skeleton ships the contract; the runtime service registration follows with the operation stages (#13 plan, #15 lifecycle).
- `PluginManagerConfig` / `PluginManagerConfigSchema` / `resolvePluginManagerConfig(input)` The §15.6 + §17 deployment Config: registry quotas (256KB code / 64MB registry / 1000 dynamic plugins), audit rotation (50MB × 5), `stateRoot` (defaults to `dshHomePath('plugin-state')`), `historyKeep` (2), `maxRuntimeApiPermissionLevel` (default `claims` = no extra cap), `swapTimeoutMs`, plus the §17 fields `grants` (empty by default), `protectedFields`, `development`, and `trustedScopes`.
- `PluginGrants` The per-plugin deployment grants: `intercept`, `claims`, `fileAccess` (`[mode, path]` entries, `write` ⊇ `read`), and `networkAccess.allow`. There is deliberately no `position` field (decision #5); review guidance for `outermost` + `intercept` plugins is a README concern, not a schema axis.
- `validateMount(definition, options)` The mount-time validation chain for §16 group 1 (manifest zod, harness-tier reachability, `@mode` ceilings, return-type property and branch vocabulary, capability-range syntax, event options) and group 2 (grant coverage, channel ceiling, source acceptance, protected fields, provenance). Every rejection is a `PluginError` with the dsh-mygo-api template message and `pluginId` set to the source definition's id once the manifest validates (a pre-validation manifest failure cannot be attributed). A successful pass returns non-fatal warnings (currently the `development-mode` provenance bypass, SEC:158).
- `assertEventOptions(options, pluginId?)` The `unsupported-event-option` guard: direct EventOptions on `env.on` are rejected because the manifest `position` is the only listener-option entry. The #12 skeleton owns the guard and message; the `PluginEnv` bridge wires it into `env.on` in the capability stage (#16).
- `deriveOrders(input)` / `buildScopeGraph(input)` / `deriveScopeOrder(...)` / `scopeMembers(...)` The pure ordering derivation (#13, §9/§11): the lexicographically smallest linear extension of the reads/writes/appends graph, computed per scope with Kahn's algorithm and a plugin-id min-heap. `orders` holds one array per scope key plus `'*'` for the unscoped-only order; end-position bands sit at the chain ends in id order; cyclic scopes are reported in `cycles` and absent from `orders`. `orderNeutral` is the per-plugin #6 flag: false exactly when the plugin declares intercept (any branch) or appends to a chain-ordered slot (PO:53).
- `evaluateConflicts(input)` The pure five-rule + claims verdicts (#13, §10-§12): `write-conflict`, `intercept-branch-conflict`, `ordering-cycle`, `veto-position-conflict`, `claims-unmanaged-incumbent`, and `shadow-undeclared`, each evaluated only where plugin scope sets intersect, sorted deterministically for preview.
- `planOperation(operation, state)` The pure plan preview (§15.3/PO:242): accepted plans carry `displaced` bystanders (plugins whose relative order changed without sharing a declared slot with the operated plugin) with the edge that displaced them, plus `wouldShadow` for dynamic installs shadowed by a static incumbent (T2-4); rejected plans preview the exact §16.2 code the operation would throw.
- `DispatchMachine` / `managedListenerOptions` / `MANAGED_META` The link ownership and containerized dispatch core (#14, §13/§16 group 5/16.4). `start()` installs the `internal/listener` bail handler and two real registrations per managed event — the outermost band on `prepend: true`, derived+innermost on one normal registration. The env bridge attaches `managedListenerOptions(meta)` to `ctx.on`; the bail diverts the listener into per-scope band arrays (from `setOrders`, the #13 derivation) and binds the entry to the caller's fiber. Every managed listener runs in a container that swallows throws (`veto-suppressed`, once per listener per boot), enforces return discipline (`next-missing` / `undeclared-veto` / `undeclared-branch`), meters own-time CPU excluding awaited `next()` windows (`quota-cpu-exceeded`, five consecutive → `onAutoDisable`, skipped intercepts surface `intercept-skipped`), and rejects direct EventOptions (`unsupported-event-option`).
- `LifecycleEngine` The operation core (#15, §14/§15.3): `install`/`uninstall`/`enable`/`disable`/`replace`/`updateConfig`, static adopt (T2-4), cached-generation return, boot recovery (T4), and `dispose`. Operations run one at a time per plugin id (`concurrent-operation`), follow T3 write ordering (create-class: runtime commit → persist → return with compensation on `persist-failed`; delete-class: persist first), and swap generations through the §14 seven-step protocol. Staging runs setup + activate against a discarded set and re-validates every tool output schema per generation (`staging-failed`); a failure before go-live leaves the old generation live with `plugin/replace-failed` emitted exactly once. Go-live swaps immutable per-event arrays and the manager-held provide/tool tables without running plugin code; the old generation is released after affected events drain, and a cached-generation return is a fresh replace whose companions are re-checked (`companion-conflict`). `swapPolicy: 'drain'|'next-idle'` waits are bounded by `swapTimeoutMs` and measured against the wall clock (`now()`), failing with `swap-timeout` carrying `policy` + `waitedMs`; own-time CPU accounting from #14 is a different clock and never pauses or extends swap waits. `io` and `fetchImpl` options inject the host file and network seams the env boundaries gate against (defaults: Node `fs/promises` and the global fetch). `persistence` injects the #17 sqlite/snapshot/audit facade; without it the engine runs in memory.
- `createPluginFs` / `fileModeForPath` / `normalizeGatePath` / `pathPrefixCovers` / `realPathOf` / `PluginIo` / `nodePluginIo` The runtime `env.fs` boundary (#16, SEC:149): a lexical path check throws `fs-denied` synchronously before any I/O, then the longest existing ancestor's symlinks are resolved and the real path is re-checked against real-resolved grant bases — a `/project` grant rejects `/etc/passwd`, `..` escapes, and symlink escapes, and a symlinked grant root is honored. `fileModeForPath` encodes the write⊃read implication: a `write` grant satisfies both read and write requests at the same path, a `read` grant satisfies read only.
- `createNetworkFetch` / `networkUrlAllowed` The runtime `env.fetch` boundary (SEC:150): the allowlist uses the same scheme/host boundary prefix as mount validation, and a denied URL throws `network-denied` before the host fetch is invoked.
- `claimEffect` / `PluginEffectQuota` The §18 registration-effect quotas: 100 listeners / 50 tools / 20 services per plugin, thrown at the registration call point (`quota-effects-exceeded`), shared across scope layers of one generation staging.
- `ToolRegistryLike` / `tools.register` bridge (Proposal A) The registry bridge that publishes each manager-held tool into the real tools registry exactly once as a live indirection (name/description/parameters/output/execute resolve through the current generation), so a replace never re-registers — no `tools/change`, stable `schemas()` position (F1 closed). The `fromCordisPlugin` facade's `ctx.tools.register` maps the raw `defineTool` output structurally onto `PluginToolDefinition`; the tool-cordis sandbox routes through the bridge when a manager is composed (F2 tool route closed). Staging enforces tool claims/shadow against the registry's global layer: `claims-unmanaged-incumbent` for claims on a raw-held slot, `shadow-undeclared` for a scoped shadow without claims, `staging-failed` for an unscoped duplicate — the later registrant never silently wins.
- `PromptServiceLike` / `createSessionPersistenceProjection` / `SessionPersistenceProjection` / `registerPromptSection` service-mapping bridge (Proposal B) `env.registerPromptSection` stages a prompt section (quota-counted against the §18 contribution bucket, finite-order validated) and the engine publishes it into the host systemPrompt service through the `promptService` seam as a live view, disposing it with the generation (HMR-safety). `env.get('sessionPersistence')` resolves a manager-curated read-only projection (listSnapshots/list/locate/inspect/load/readFrom/prepare) through the `sessionPersistence` seam when the declaration names it; the write methods (`create`/`append`) are present as throwing stubs so a call physically fails instead of silently returning `undefined` (write surface deferred to the first write consumer). The facade maps `ctx.systemPrompt.section` and `ctx.sessionPersistence` onto these surfaces; raw `inject` stays un-honored (declaration-is-load-bearing).
- `createRateLimitedLogger` The SEC:71 logger gate: 1000 lines per plugin per minute; excess lines are dropped and the plugin is warned once per window.
- `RegistryStore` / `InMemoryRegistryStore` The persistence seam (§22.1 rows: write-once `gens` plus a small per-plugin `status` row, opaque TEXT with `v: 1` record versions) and the in-memory implementation with `fail(table)` write-failure injection and `snapshot()` for crash tests. `usage()` feeds the T6 registry quotas; `crashAfter(table)` injects a power loss right after a write's durability point (T3 crash matrix).
- `SqliteRegistryStore` / `openSqliteRegistryStore` / `RegistryRowError` The sqlite implementation of the seam over the storage-domain form (real sqlite backend, one database file per profile). Values stay opaque TEXT; unparsable rows surface `RegistryRowError` so boot recovery quarantines them as `damaged-record`.
- `pluginRegistryDomainSpec` / `sanitizeProfileName` / `fnv1a` The per-profile domain declaration `plugin_registry_<profile>` (§22.1): `gens`/`status` tables, version 1, `recovery: 'reset'`, and the written profile-sanitization rules (lowercase, `_` substitution, `p_` prefix, FNV-1a collision suffix).
- `SnapshotStore` / `SnapshotMeta` The state-snapshot files (§22.2): `plugin-state/<profile>/<id>/<gen>.state.json`, temp-write + rename, sha256/byte metadata on the status row, hash-verified reads (mismatch = no snapshot + warn), and boot GC over orphan files.
- `AuditLog` / `AuditClass` The deployment audit stream (T5): append-only JSONL at `plugin-state/<profile>/audit.jsonl`, 0o600, rotation by `auditMaxBytes` × `auditKeepFiles`, tolerant readers (`since`/`byPlugin`/`tail`), and the §22.3 closed class set.
- `RegistryPersistence` The composed facade: opens the profile domain, snapshot store, and audit log, and routes `domain/reset` into the audit stream (`medium-reset`, T4-5). Composition wiring of the facade into the runtime is part of #18.
- `PluginManagerService` / `PluginManagerServiceConfig` The Loader-facing `ctx.pluginManager` service (#18): `storage`/`storageDomain` injected, Config = the §15.6/§17 surface plus `profile` and `cpuBudgetMs`. Init opens the per-profile persistence, builds the dispatch machine with the two composition wirings (`onAutoDisable` runs the engine's disable protocol with reason `cpu-quota`; dispatch violations flow into the audit stream with §22.3 classes), recovers, and exposes the full §15.3 operation surface. Inline sources are evaluated as in-process modules exporting a `PluginDefinition`; npm sources reject with `package-not-resolvable`. Host-side audit readers (`auditSince`/`auditByPlugin`/`auditTail`, T5-4) close the SEC:153 "readable through a separate service" face; `PluginEnv` never sees them.
- `EVENT_VOCABULARY` / `PluginEventVocabularyEntry` The generated harness vocabulary: per event, its dispatch mode, the top-level property names of its real return type, and the discriminant labels of a decision-union return type. `src/event-vocabulary.ts` is produced by `pnpm run gen-cordis-catalog` from the same Typert AST walk as `docs/cordis-catalog/events.md` and the `tool-cordis` API catalog, and is freshness-gated by `pnpm run verify-cordis-catalog` — never edit it by hand and keep no handwritten event allowlist in this package.

## Design contract

Mount-time reachability is tier-derived, not allowlisted: an event is manageable exactly when it appears in the generated harness vocabulary (`@deepseek-ai/dsh-*` declarations); the inherited tier (`internal/*`, hmr, loader, exit) is absent and therefore `event-not-mountable`. Declared `reads`/`writes`/`appends` names and intercept `returns` branches resolve against the event's real return type from the same projection, so a `writes: ['modle']` typo fails at mount instead of silently ordering nothing.

The mount-time coverage rules are intentionally concrete: file-access grants cover a declared entry by mode implication (`write` ⊇ `read`) and path-boundary prefix; network grants cover a declared URL by scheme/host boundary prefix (`https://example.dev` covers `https://example.dev/api` but not `https://example.dev.evil/`). Runtime `..`/symlink normalization and allowlist enforcement live at the `env.fs`/`env.fetch` boundaries (#16) and execute the grant set, not the declared set: a request outside the grants is rejected before any host read/write or network activity, and `state-rejected` captures are warned (16.4) with the replace step-3 failure path.

All messages and machine-readable details come from `@deepseek-ai/dsh-mygo-api`'s `PluginError` templates; this package never formats its own wording for the §16.2 codes.

The derivation and plan verdicts are a pure function of the validated installed set (`PlanState`): no install history, config line order, import resolution order, or timing enters them. Scope sets, slot classification (`slotKinds`, defaulting unknown slots to `chain-ordered`), and slots held outside the manager (`heldOutsideManager`) are explicit inputs the caller supplies from its own runtime snapshot.

Dispatch is containerized because the containment is load-bearing (§7): Cordis's `Events.emit` runs listeners without a try-catch, so a throwing managed listener would veto the dispatcher and starve its peers. The machine holds the only real registrations, walks one immutable array snapshot per dispatch (PO:244), and disposes without residue (PO:245).

The lifecycle engine treats each generation as an immutable `{manifest, code, resolvedConfig}` snapshot with history bounded by `historyKeep`. All runtime effects go through the dispatch machine and the manager-held provide/tool tables, so go-live never runs plugin code: a crash after the status pointer write (replace step ⑤) leaves the new generation as the durable current and the T4 boot path re-stages it, while a crash between the generation row and the pointer leaves an orphan that boot GC removes. Staging is cross-scope atomic — every existing scope must stage before any array is swapped; a failure keeps all scopes on the old generation. Manager-held `provide` values are replaced in place, so an unchanged capability keeps its dependents mounted; dropped provides run the dependent check first (`dependent-exists`). Tool names are globally unique: the staging assertion rejects duplicates, and a replaced-away tool name is released at go-live, so hot-swapping never emits `tools/change` and never disturbs `schemas()` order (HP:137).

The #17 persistence layer makes the registry durable per profile. Write ordering follows T3: create-class operations (install/enable/replace) commit runtime state, write the generation row, then flip the status pointer (persist-failed compensates); delete-class operations (uninstall/disable) persist first. A power loss between writes leaves either an orphan generation that boot GC collects or the new pointer already durable — boot recovery re-stages it. Boot recovery (T4) revalidates every row against the current environment and reports restored / shadowed / quarantined (validation-failed, damaged-record, package-not-resolvable) / gc rows; a medium-level damage class discards and reopens the domain once (`medium-reset`, audited). Disabled rows are fully recovered: their manifest is restaged without mounting, so `plugins()` shows their declarations and dependency edges hold; `enable` then mounts (and restores the state snapshot) on the recovered generation. State snapshots are written before the status pointer (T3 rule 4) and restored across boot with hash verification. Quotas are evaluated at install (code ≤ `maxCodeBytes`, projected registry bytes ≤ `maxRegistryBytes`, rows ≤ `maxDynamicPlugins`).

The #18 factory integration ships the bundle rows that make the manager real: `dsh-base` adds storage / storage-sqlite / storage-domain / dsh-mygo, with the domain default route flipped to sqlite (`plugin-state/registry.db`) and the launcher exporting `DSH_PROFILE` for the per-profile registry unit. `dsh-web-app` restates the storage-domain row with `backend: sqlite` plus explicit `routes` naming `workspace` and `session_projcache` to json, so those static named domains keep their json shape while the registry goes sqlite. A bundle row referencing a `definePlugin` package mounts `toCordisPlugin(definition)` (from `@deepseek-ai/dsh-mygo-api`), whose `pluginManager` inject self-adopts the entry as a managed static plugin — the REAL-composition suite proves the chain end to end.

PO:243's no-core-modification property is enforced by the composition gates: `verify-runtime-closure` (101 packages closed) and `verify-cordis-config`; the manager's only core dependency is the unmodified `@deepseek-ai/dsh-mygo-api`.

## Known Limitations and Deferred Work

- **`env.on` has no options parameter** — direct EventOptions are structurally impossible at the PluginEnv seam; the dispatch machine rejects any smuggled options through the bail (`unsupported-event-option`).
- **Serial intercepts must declare an empty `returns` list** — serial events have no decision-union labels (veto is the `isBailed` three-way test), so any `returns` entry fails `unknown-property`; a granted `intercept: []` declaration is the supported shape.
- **Unscoped npm packages have no trusted-scope path** — the §15.1 source union carries no attestation field, so an npm package without a scope is `provenance-rejected` unless `development: true` bypasses with a warning.
- **In-process memory quotas remain a documented soft limit** — §18's 50MB heap row needs an isolate/worker boundary to be hard (SEC:70 hedge); v1 has no such boundary, so the limit is logged, not enforced.
- **Tool claims and tool shadowing preview at plan time, enforced at staging** — the pure module sees manifest declarations only, so plan previews stay declaration-only; the engine (with registry knowledge from the tools.register bridge) enforces `shadow-undeclared` / `claims-unmanaged-incumbent` / `staging-failed` for tool names at staging.
- **Prompt sections publish globally in v1** — scoped `registerPromptSection` calls are recorded with their scope but the manager publishes one name-keyed section into the host service; per-scope prompt sections are a later integration point.
- **sessionPersistence write surface is deferred** — the projection's `create`/`append` reject with a named message (REAL-asserted); the write surface reopens only when the first managed plugin needs to write sessions, at which point its consumer and permission attribution are decided.
- **Two claimants of one slot on intersecting scopes reject with `claims-conflict`** — the 2026-08-08 writeback added the code for the PO note's claims-pair sentence; tool-claim pairs against managed incumbents are enforced by the engine at staging, and against raw incumbents by `claims-unmanaged-incumbent`.
- **Unknown-id enable/disable/replace preview `plugin-not-found`** — the 2026-08-08 writeback added the caller-bug code (`<subject>-not-found` family); uninstall stays the documented idempotent exception.
- **Install onto an existing dynamic id previews `concurrent-operation`** — same-id overlapping operations are rejected (HP:150); a static incumbent instead accepts with `wouldShadow: true`.
- **Slot classification lives in the input until the catalog reports it** — PO:236's catalog reporting of host-sorted vs chain-ordered slots is a later integration point (#19); the pure function consumes `slotKinds` as given.
- **The machine dispatches only plugins present in the derived orders** — order participation is the #13 derivation's contract; the lifecycle engine refreshes orders after every topology commit, so a live plugin is never silently left outside after a lifecycle operation.
- **Scope keys are opaque at the machine seam** — `scopeKeyOf` maps a dispatch receiver to the string key the orders use; the runtime `ScopeKey` ↔ string mapping is the env bridge's job (#16).
- **Per-plugin CPU budgets are global to the machine in #14** — §18's per-plugin Config wiring arrives with the lifecycle/env stages; the machine takes one `cpuBudgetMs` for now.
- **Quarantined rows revalidate every boot but stay quarantined** — a row marked `quarantined` is re-checked against the current environment, and when validation passes it remains visible as a status-only row (empty declarations) until an operator replaces or reinstalls it. The spec's T4-3 retry wording is interpreted conservatively here (see the #17 Agent Note).
- **Cross-process operations converge at restart** — sqlite WAL makes writes safe, but a second process's install/uninstall is invisible to a running one; an uninstall racing a replace can resurrect the plugin at restart (`cross-process-resurrected`, T3 Known Limitation).
- **Profile deletion is an operator action** — destroying the domain unit and deleting `plugin-state/<profile>/` is wired at the composition level (#18), not inside the engine.
- **`plan()` is async** — 2026-08-08 ruling #4: install/replace sources resolve through the manager's resolver inside the plan, as a pure read with zero staging side effects (no fiber, no hooks, no registry writes); uninstall/enable/disable derive the candidate from the managed records. The temporary `staging-failed` (stage `plan`) behavior was removed.
- **`tool-cordis`'s cordis_mount/unmount lifecycle routing stays deferred** — the tool remains examples-only; tool registrations from a mounted raw plugin route through the manager bridge when composed (F2 tool route closed), but the full §23.2 declaration/permission bridge for event-declaring raw plugins is not wired in this stage.
- **Inline source evaluation is in-process** — model-authored inline code runs through `new Function` by the service's resolver; upstream sandboxing is the host tool's responsibility (tool-cordis), matching decision #11's reference-not-fetch stance.
- **The tools.register bridge closes F1/F2** — managed tools are published to the real registry through one live indirection per name; `schemas()` order is stable across replace with no `tools/change` (REAL-composition assertions), and tool registrations from bridged raw plugins (including the tool-cordis sandbox) route through the manager. The remaining §23.2 permission bridge for event-declaring plugins is a separate deferred item.
- **`ctx.pluginManager` is not yet listed in the generated services catalog (F3-half)** — the `plugin/*` events are catalogued and the vocabulary includes them; the services catalog misses the key due to a typert workspace-analyzer export-resolution gap. Owner: typert generator. Trigger: a catalog consumer needing the service entry, or the analyzer fix.
- **host-sorted vs chain-ordered slot reporting is input-only (F4)** — `slotKinds` is consumed from the caller; catalog reporting of the two classes is deferred. Owner: PO:236 catalog-report item. Trigger: a catalog slot-classification consumer.
- **The REAL cold-module-cache transcript snapshot is not recorded (F5)** — pure-function input-permutation determinism is tested; the runnable example transcript (permuted cordis.yml + cold module cache) is deferred. Owner: snapshot-harness example suite. Trigger: an example-harness consumer.
- **A symlinked grant root resolves to its target** — the real-path gate honors a grant whose configured base is a symlink by resolving the base; grants pointing into a symlinked directory work through the target, never through an escaping link.
- **The hot-swap cache is event-keyed** — an old generation is retained only while an affected event has in-flight dispatches; returning to it later is a full replace against the current companion set.
